# 2.3.2 Binary Flag Temporal Manual Problem Review

This review checks the binary flag temporal decisions feature-by-feature using feature meaning, not only statistical thresholds.

## Manual checking rule used

1. Take one binary feature at a time.
2. Understand the feature meaning from its name and source family.
3. Check whether the temporal route, risk level, and manual-review decision match that meaning.
4. If the temporal decision is reasonable, keep it.
5. If the temporal decision is too aggressive, too generic, or source-blind, correct the decision.
6. Final output keeps only feature-level decisions for the next step; raw statistical information is not needed again for this section.

## Logic fixes to remember for future temporal cells

- Do not mark almost every binary flag as manual review only because it has a rare side or group redundancy.
- For binary flags, rare positive can be meaningful; do not treat sparsity as a drop signal.
- Test constant is only a serious issue when the train positive side is meaningful, not when it is tiny.
- `inst_*` features should be recognized as installment-history features.
- `has_*_history` features should be treated as direct history availability indicators.
- Structured missing in history-source flags should be handled as no-history/unknown signal, not dirty missing.
- Single-observed flags should be validated later, but not dropped in univariate EDA.
- Group redundancy belongs to multivariate/model validation, not this univariate temporal step.
- No binary flag should be dropped at this stage without target, bivariate, multivariate, leakage, and model-validation evidence.
